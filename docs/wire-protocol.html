MAX9860 EVKIT Wire Protocol

Everything needed to drive the MAX9860 evaluation board — clock tree, codec and S/PDIF transceiver — without the Maxim Windows application. The clock tree is the part you cannot reach any other way. Byte sequences below were captured off the live link, not inferred.

Why any of this is necessary

The board does nothing on its own. Out of the box it produces no sound — the vendor application does nothing but set registers, and it does so in a way that had to be reverse-engineered to reproduce.

Most of that you can sidestep. Open JU8 and the MAX9860's I²S and I²C lines are yours; the codec's control interface is ordinary I²C at 0x20 and needs no command module at all. The CS8427 can be ignored entirely if you aren't using S/PDIF.

The clock tree is the exception, and it is the reason this document exists. The two mux selects and both oscillator enables land on MAXQ2000 port pins — P0.1, P0.2, P0.4, P0.5 — and nowhere else. The board's eleven jumpers cover microphone wiring, the supply rails and the JU8 interface takeover; none of them touches clock selection. So there is no way to choose between the 12.288 MHz oscillator, the 13 MHz oscillator and the recovered S/PDIF clock, or to gate either oscillator, except by driving those four GPIOs through the command module.

Which sets the priorities for anyone implementing against this board:

An external clock injected at JU8 row 5 avoids the mux, but does not avoid the problem: the on-board oscillators are still gated by those same GPIOs, so you cannot reliably guarantee they are silent without driving them.

Transport

The board carries an FT232 bridged to an on-board MAXQ2000 that runs the command-module firmware. You talk to the MAXQ2000, never to the codec directly — it performs the I²C and SPI cycles on your behalf.

Two routes to the same silicon, and they are mutually exclusive: the FTDI D2XX API (FT_Open device 0) or the virtual COM port. While one holds the device the other returns access-denied. The stock application uses D2XX; a portable driver is simpler over the COM port.

Every exchange is strict request/response — write a command, read its reply. No framing, no length prefix, no checksum, no line terminators. Reply length is fixed per command.

With one exception: on open the module emits an ASCII banner, "Maxim MINIQUSB V01.05.39 >", 26 bytes with no terminator. It arrives unprompted and will otherwise turn up glued to the front of your first command's reply. Drain the port before the first command.

Status bytes follow a rule

For the Ax family the acknowledgement is the command's first byte with its high nibble changed from A to B: A0…→B0, AD→BD, AF→BF. Pin writes answer F0, and FA is the error / not-available reply throughout.

Do not send 0xA9

It puts the firmware into a continuous ASCII echo mode that saturates the link at full line rate and does not stop on its own. Recovery is closing and reopening the port. Nothing else in the A0–AF range behaves this way.

Reaching the codec over I²C

The MAX9860 answers at 0x20 — the eight-bit form, already shifted, exactly as you place it in the command. One command carries the whole transaction.

read register 0x02 from the codec
TX  A0 05 01 01 20 02     write 1 byte, read 1 byte, addr 0x20, register 0x02
RX  00 B0                 register value 0x00, then the B0 acknowledgement

write 0x80 to register 0x02 — read count zero
TX  A0 05 02 00 20 02 80
RX  B0

Read counts above one return that many bytes ahead of the B0. A device that does not acknowledge yields FA in place of the data.

Reaching the transceiver over SPI

The CS8427's control port is on the MAXQ2000's hardware SPI, but chip select is not automatic — it is plain GPIO on K9, and you bracket the transfer with it yourself.

Each byte is its own AF command, but they can be pipelined into a single write, and the vendor application always does: all three bytes of a register access go out together and three replies come back at once. Both forms are identical on the wire — but a capture tool that assumes one command per write will read only the first byte and silently drop the rest.

captured: write CS8427 register 0x04 (Clock Source) = 0x48
TX  F9 00                  K9 low — assert chip select
RX  F0
TX  AF 20  AF 04  AF 48    chip 0x20 = write, MAP 0x04, data 0x48
RX  FF BF  FF BF  FF BF    one <miso> BF pair per byte
TX  F9 01                  K9 high — release chip select
RX  F0

Write framing is chip byte, MAP, then data, all inside one /CS window. Chip is 0x20 to write; bit 7 of MAP auto-increments the register pointer across a burst.

Reading takes two transactions, not one

This is the part that will waste your afternoon. Putting 0x21, MAP and a dummy byte in a single /CS window returns zeros. The register pointer has to be set by its own write transaction first, then read in a second one.

verified: write 0x48 to Clock Source, then read it back
--- does NOT work: one transaction ---
TX  F9 00 · AF 21 AF 04 AF 00 · F9 01
RX  MISO FF 00 00                       always zero

--- works: address, then read ---
TX  F9 00 · AF 20 AF 04 · F9 01         write chip byte + MAP, no data
TX  F9 00 · AF 21 AF 00 · F9 01         read chip byte + one dummy
RX  MISO FF 48                          second MISO byte is the register

MISO during the chip-address byte is always 0xFF (the bus idles high); the register value arrives on the following byte.

All six registers are readable — verified by writing the distinct values 0x11…0x66 and reading each one back, all six matching. A register that reads 0x00 genuinely holds zero; it is not a failed readback. So a host program can recover the full transceiver configuration from the hardware rather than caching it, which the vendor software does not do.

Hold K4 high before expecting the transceiver to answer; it is the reset line and a low leaves the part held down.

The board remembers nothing

There is no non-volatile settings store anywhere in this design. Every configuration you want must be pushed over the wire, every session.

The only EEPROM on the board is U9, a 93C46 on the FT232's EECS/EESK/EEDATA pins — that holds the USB descriptor (VID, PID, serial) and is not reachable from the command module. The firmware's A0 06/A0 07 EEPROM support targets an I²C part on a daughter board; there isn't one here.

The vendor application's own Reset confirms it behaviourally: it writes every register blind and never reads anything first to recover prior state. Each read in that sequence is a read-back of the value just written.

But the parts are volatile, not amnesiac. The codec and transceiver hold their registers for as long as the board stays powered, so closing and reopening a host program does not blank them — they keep the last values written until power is removed, or until something pushes a fresh configuration. "Starts blank" is true only after a power cycle.

That tail is an independent check on the clock table: CLK_SEL=0, OX_SEL=0, 13 MHz enable high is exactly the documented 13 MHz selection.

Because nothing is stored on the board, a host program does not have to reset at startup — every part of the state is recoverable by reading: codec registers over I²C, transceiver registers over SPI, and the clock configuration from the pins themselves (E0|K for K2, K3, K5, K6). Reading rather than resetting means attaching to a running board without disturbing it.

Things that will cost you an afternoon

K1 is an input

It is the codec's interrupt output. The pin-write command will happily accept F1 01 and you will be driving against a live output.

K13 and K14 answer FA

Not a bus fault — those indices are simply absent on this hardware. Treat FA from a read as "no such pin", not as an error worth retrying.

D2XX and the COM port lock each other out

Whichever opens first wins; the other gets access-denied until it is released. Closing the vendor application is not always enough — it holds the D2XX handle across a disconnect.

Both oscillators off is a valid state

It means "external clock". If MCLK is dead and both enables read 0, the board is waiting on a jumper, not misconfigured.

Don't copy the vendor's reset ordering

Its Reset writes all six CS8427 registers while K4 is low, raises K4 afterwards, and never rewrites them. If K4-high is the operational state — which normal running suggests — those writes went into a part held in reset. Release K4 first, then configure.

Commands batch inside one write

A write is not a command boundary. Three AF commands routinely travel in one transfer with three replies concatenated behind them. Parse the stream by command length, not by write boundary, or you will decode the first byte of each burst and lose the rest.
